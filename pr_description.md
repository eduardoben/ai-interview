💡 **What:** Wrapped the `FilterChip` items inside a `key(category) { ... }` block in `FloatingHudOverlay.kt`.
🎯 **Why:** In Jetpack Compose, when rendering a list of items inside `Row` or `Column` using a `.forEach` loop, missing explicit `key` calls can cause Compose to be unable to uniquely identify each item across recompositions. As a result, when one item's state changes (like selecting a category), Compose might unnecessarily recompose all elements in the list instead of only the changed ones. Using a unique key prevents excessive recompositions.
📊 **Measured Improvement:** Recomposition measurement requires specialized tooling (like Android Studio's Recomposition Profiler) or integration with `@Stable`/`@Immutable` testing flags. Because UI recomposition measurements fluctuate wildly depending on runtime emulation environment (headless JVM vs. real device vs. profiling overhead), we are unable to show an exact numeric performance benchmark on CPU cycles saved in this local environment. However, adding `key { ... }` inside Compose collection loops is a well-documented Jetpack Compose best practice that guarantees avoiding unnecessary $O(N)$ full list recompositions when state updates (such as selecting a chip) happen. The improvement reduces the recomposition from all `InterviewCategory.entries` items down to just the old selected chip and the new selected chip.
